# Memory Management and Streaming

Forge streams huge procedural worlds from SSD into a Vulkan renderer whose geometry (cluster LOD DAG), textures (virtual textures) and per-frame data live in device-address buffers behind one bindless set. The owner asks for "memory optimization with the best memory manager techniques, Resizable BAR too, load data from the SSD efficiently". Two in-house facts frame the question: on the dev PC `gpu-allocator`'s `CpuToGpu` location already lands per-frame data in host-visible device-local memory, so Resizable BAR is in use whether the engine knows it or not; and the previous engine streamed terrain through a 3,072-slot pool with last-used eviction and paid with LOD popping, an eviction-policy bug rather than a bandwidth one. This file collects the verified sources for a memory and streaming design on the RTX 5070 Ti (16 GB GDDR7, PCIe 5.0) with 61 GB of RAM and the RTX 3080 server (PCIe 4.0), Windows first and Linux later, and ends with an opinionated design and the demo that proves it.

> **State of the art in five sentences.** Engines do not `malloc`: they group allocations by lifetime into arenas, tagged block heaps and pools (Naughty Dog's 2 MiB tagged heap, DICE's scope stacks, Fleury's reserve-then-commit arenas), keep a general-purpose allocator such as mimalloc only for the long tail, and watch every byte through Tracy. GPU memory is sub-allocated from 256 MiB blocks with a TLSF allocator (VMA 3.x), budgeted through `VK_EXT_memory_budget`, aliased for render-graph transients, defragmented incrementally on the transfer queue, and written through Resizable BAR only for sequential, never-read per-frame data, because the measured gain is a few percent of frame time, not bandwidth. Streaming is a GPU feedback loop: the GPU reports which virtual-texture and cluster pages it wanted (Nanite: fixed 128 KB pages, priority by screen error, root page always resident), the CPU issues unbuffered 64 KB+ reads through IOCP/IoRing or io_uring, data is decompressed on the GPU (GDeflate through `VK_EXT_memory_decompression`, Zstandard arriving in DirectStorage 1.4 with an open shader) or on spare cores at 1.5–4 GB/s each, and residency is driven by need, not recency. DirectStorage itself remains a DirectX 12 runtime, so a Vulkan engine reuses its formats, shaders and request rules, not its API. Consoles set the bar (PS5 5.5 GB/s raw, 8–9 GB/s typical decompressed; Xbox 2.4/4.8 GB/s plus sampler feedback streaming for ~2.5× effective), and PC engines such as Snowdrop and Ghost of Tsushima show that the budget must come from the OS, eviction must be page-granular, and over-commitment turns a 16 GB card into a 2 GB/s PCIe crawl.

## 1. CPU allocators and engine memory strategy

**Masmano, M., Ripoll, I., Crespo, A., Real, J. "TLSF: a New Dynamic Memory Allocator for Real-Time Systems." ECRTS 2004.** [paper] [foundational]
https://doi.org/10.1109/ecrts.2004.35 — reference C implementation: https://github.com/mattconte/tlsf
Two-Level Segregated Fit: a first-level bitmap of power-of-two size classes and a second-level linear subdivision give O(1) `malloc`, `free`, `realloc` and `memalign` with bounded fragmentation. Conte's BSD implementation costs 4 bytes per allocation and ~3 KB per pool and is deliberately not thread-safe. VMA 3.0.0 (Mar 2022) made TLSF its default.
*Bearing:* The allocator inside every Forge GPU memory block and the CPU large-object heap; predictable cost is what a frame budget needs.

**Ginger Bill (Bill Hall). "Memory Allocation Strategies," parts 1–6. gingerbill.org, 2019–2021.** [web] [still-current]
https://www.gingerbill.org/series/memory-allocation-strategies/
Part 1 (Feb 2019) rejects the stack-versus-heap dualism; parts 2–4 (Feb 2019) implement the linear/arena, stack and pool allocators in C; parts 5–6 (Nov–Dec 2021) add free-list and buddy allocators, each under 200 lines.
*Bearing:* The vocabulary and reference code for Forge's allocator layer; each maps one-to-one to Rust.

**Fleury, R. "Untangling Lifetimes: The Arena Allocator." 2022; Muratori, C. "Dynamically Growing Arenas." Handmade Hero day 341, 2016.** [web] [still-current]
https://www.dgtlgrove.com/p/untangling-lifetimes-the-arena-allocator — https://guide.handmadehero.org/code/day341/
Fleury (23 Sep 2022): `malloc`/`free` with arbitrary sizes and lifetimes breed "rat's nests"; group allocations by lifetime, expose push/pop/clear, keep per-thread scratch arenas with temporary markers, and on 64-bit reserve a huge range (his example is 64 GB) and commit pages as the arena grows. Muratori (21 Oct 2016) makes the Handmade Hero `PushSize` arena growable by chaining `VirtualAlloc` blocks.
*Bearing:* Forge's frame arena and job scratch arenas: reserve once, commit on demand, pop per frame, no per-object free.

**Fredriksson, A. "Scope Stack Allocation." DICE, 2010.** [talk] [foundational]
https://www.ea.com/frostbite/news/scope-stack-allocation — PDF: https://media.contentapi.ea.com/content/dam/eacom/frostbite/files/scopestacks-public.pdf
Consoles are embedded systems with fixed memory where heap allocation is expensive through fragmentation and poor locality; scope stacks lay out object hierarchies linearly, run destructors in dependency order on rewind, allocate in a single cycle and give a deterministic memory map.
*Bearing:* One scope per streamed world cell, rewound in bulk on unload with `Drop` in reverse order.

**Gyrling, C. "Parallelizing the Naughty Dog Engine Using Fibers." GDC 2015.** [talk] [foundational]
https://gdcvault.com/play/1022186/Parallelizing-the-Naughty-Dog-Engine — slides: https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf
On PS3 many linear allocators each sized for the worst case wasted 100–200 MiB because they never peaked together. The PS4 tagged heap: 2 MiB blocks (one large-page TLB entry), each owned by a 64-bit tag, no `Free(ptr)`, bulk free by tag; every allocator keeps one block per worker thread, so 99.9% of allocations take no lock, and 99% of allocations are under 2 MiB.
*Bearing:* Forge's job memory: tag = (frame, stage), per-worker blocks, bulk free when a stage retires; it also ends "one arena per system sized for the worst case".

**MacDougall, A. "Building a Low-Fragmentation Memory System for 64-bit Games." GDC 2016 (Sony London Studio).** [talk] [still-current]
https://www.gdcvault.com/play/1023005/Building-a-Low-Fragmentation-Memory
The abstract (the deck is members-only): current-generation "huge virtual address spaces" can "prevent many of the problems encountered with memory fragmentation in the last generation". Guerrilla's Decima allocator (§4) shows the same idea in numbers.
*Bearing:* Reserve address space generously, commit physical pages sparsely, let the virtual layout absorb fragmentation.

**Leijen, D. et al. mimalloc; Jansson, M. rpmalloc; Li, R., John, L. K., Yadwadkar, N. J. "Old is Gold: Optimizing Single-threaded Applications with Exgen-Malloc." arXiv 2510.10219, 2025.** [code] [paper] [still-current]
https://github.com/microsoft/mimalloc — https://microsoft.github.io/mimalloc/bench.html — https://github.com/mjansson/rpmalloc — https://arxiv.org/abs/2510.10219
mimalloc (MIT) shards free lists per page and frees across threads with lock-free CAS; its README benchmarks (AMD 5950X, Jan 2021, flagged as dated by the authors) put it ahead of jemalloc, tcmalloc and Hoard with memory "up to 25%" higher in the worst case, and the README now recommends the v3 line. rpmalloc (Epic's Jansson; Unlicense/MIT) is ~3,300 lines of single-file C with thread-local heaps. The 2025 paper, on mimalloc-bench, shows even mimalloc leaving 0.1–25% memory on the table for single-threaded workloads.
*Bearing:* mimalloc is Forge's global allocator for the long tail and third-party crates; the hot path never touches it.

**Taudul, B. Tracy profiler; Tosic, M. MTuner; Superluminal.** [code] [still-current]
https://github.com/wolfpld/tracy — https://docs.rs/tracy-client/latest/tracy_client/ — https://github.com/milostosic/MTuner — https://superluminal.eu/
Tracy's `TracyAlloc`/`TracyFree` (S-variants capture call stacks) give memory-usage graphs, active-allocation lists, a rewindable memory map and per-zone memory statistics; `tracy-client` 0.19 ships `ProfiledAllocator` around any `GlobalAlloc`. MTuner records the full time history of memory operations with replay and leak detection (BSD-2; now archived read-only). Superluminal is an 8 kHz sampling CPU profiler with Rust demangling; it is not a memory profiler.
*Bearing:* Every Forge allocator, CPU and GPU, reports through Tracy from day one.

## 2. GPU memory: sub-allocation, Resizable BAR, aliasing, budgets, sparse

**Sawicki, A. "Memory Management in Vulkan and DX12." GDC 2018 (AMD); Tovey, S. "Vulkan Memory Management." Vulkanised 2018 (AMD).** [talk] [foundational]
https://gdcvault.com/play/1025458/Advanced-Graphics-Techniques-Tutorial-New — slides: https://media.gdcvault.com/gdc2018/presentations/Sawicki_Adam_Memory%20management%20in%20Vulkan.pdf — https://gpuopen.com/events/gdc-2018-presentations/ — Tovey: https://www.khronos.org/assets/uploads/developers/library/2018-vulkanised/03-Steven-Tovey-VulkanMemoryManagement_Vulkanised2018.pdf
The canonical PC memory-type map: `DEVICE_LOCAL` (VRAM), `HOST_VISIBLE` (system RAM, write-combined, GPU reads cross PCIe), `DEVICE_LOCAL | HOST_VISIBLE` (in 2018 a 256 MiB BAR pool on AMD only: "don't read from it") and `HOST_VISIBLE | HOST_CACHED` for readback. Rules that still hold: sub-allocate from 256 MiB blocks, never allocate or free blocks during gameplay, over-commitment silently migrates blocks, leave 20% of `DEVICE_LOCAL` and 33% of the BAR heap free, persistent mapping is fine, the copy queue is for PCIe transfers and background defragmentation ("do your transfers long before the data is needed"), GPU-to-GPU copies are faster on the graphics queue. Tovey adds "just 16 allocations fills 4 GiB", separate blocks for small and large allocations, and ">50% memory saved in some titles" by aliasing.
*Bearing:* Forge's block sizes, the 20/33% headroom rule, persistent mapping and the transfer-queue-for-PCIe rule come from here.

**AMD GPUOpen. Vulkan Memory Allocator 3.x. 2017–2026.** [code] [still-current]
https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator — https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator/blob/master/CHANGELOG.md — https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/defragmentation.html — https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/usage_patterns.html
MIT single header. 3.0.0 (25 Mar 2022) made TLSF the default, rewrote defragmentation as incremental passes (a begin call returns the move list, the application recreates and copies, the end call frees sources; `maxBytesPerPass`/`maxAllocationsPerPass` bound each frame), added a virtual allocator, budgets via `VK_EXT_memory_budget` and aliasing helpers; 3.4.0 (Jun 2026) is current. The "advanced data uploading" pattern, `HOST_ACCESS_SEQUENTIAL_WRITE | ALLOW_TRANSFER_INSTEAD`, picks BAR memory when it exists and falls back to staging, since cards have "only 256 MB of BAR by default, unless ReBAR is supported and enabled in BIOS".
*Bearing:* The reference design whether or not Forge links it: TLSF blocks, budget-aware, frame-bounded defragmentation with app-side copies, "sequential write, transfer instead" uploads.

**Sawicki, A. "Vulkan Memory Types on PC and How to Use Them." asawicki.info, 2021; Pettineo, M. "GPU Memory Pools in D3D12." 2022.** [web] [still-current]
https://asawicki.info/news_1740_vulkan_memory_types_on_pc_and_how_to_use_them — https://therealmjp.github.io/posts/gpu-memory-pool/
Sawicki (21 Feb 2021): Intel iGPUs expose one heap where everything is `DEVICE_LOCAL | HOST_VISIBLE`; NVIDIA a VRAM heap and a system heap; AMD adds the 256 MB BAR heap; with Resizable BAR "there is no longer a separate 256 MB heap … entire main DEVICE_LOCAL heap is also accessible via a HOST_VISIBLE memory type", the driver uses it too, and layouts must be queried. Pettineo (Jul 2022) gives the scale (~448 GB/s VRAM versus ~16 GB/s over PCIe 3.0) and the ring-buffer pattern for per-frame staging.
*Bearing:* Forge detects three layouts at start (UMA, discrete, discrete with ReBAR) and picks an upload policy per layout; the owner's `CpuToGpu` observation is the third.

**AMD. "How to get the most out of Smart Access Memory (SAM)"; "RDNA Performance Guide." GPUOpen, 2021–2024.** [web] [still-current]
https://gpuopen.com/learn/get-the-most-out-of-smart-access-memory/ — https://gpuopen.com/learn/rdna-performance-guide/
SAM is AMD's name for ReBAR (Jun 2021). BAR memory is uncached write-combined VRAM: write sequentially or with high locality, align to 64 bytes, avoid strides and random access, never read, keep buffers ≥64 KiB. Copies of VRAM-resident data ran "5x as fast" on the graphics/compute queue than on the transfer queue; use the copy queue when the result can wait. The RDNA guide: 256 MB heaps, with ReBAR "entire VRAM is accessible for the CPU" using sequential `memcpy` only, copy queue for PCIe, and sparse resources discouraged "based on their performance hit both on GPU and CPU".
*Bearing:* The write discipline for Forge's ReBAR ring (64-byte-aligned sequential copies from a CPU shadow, no reads) and AMD's verdict on sparse.

**NVIDIA. "Optimizing DX12 Resource Uploads to the GPU Using GPU Upload Heaps," 2021/2023; Microsoft. "D3D12 GPU Upload Heaps" specification; "System and Driver Support for Resizable BAR," 2025; NVIDIA GeForce. "Resizable BAR Support," 2021; Puget Systems, PCIe 5.0 bandwidth, 2025.** [web] [recent]
https://developer.nvidia.com/blog/optimizing-dx12-resource-uploads-to-the-gpu-using-gpu-upload-heaps/ — https://microsoft.github.io/DirectX-Specs/d3d/D3D12GPUUploadHeaps.html — https://learn.microsoft.com/en-us/windows-hardware/drivers/display/resizable-bar-support — https://www.nvidia.com/en-us/geforce/news/geforce-rtx-30-series-resizable-bar-support/ — https://www.pugetsystems.com/labs/articles/impact-of-pcie-5-0-bandwidth-on-gpu-content-creation-performance/
Microsoft's driver documentation: discrete GPUs claim a 256 MB I/O region by default; on ReBAR hardware WDDM 2+ renegotiates the BAR after firmware init "to expose the entire VRAM" as one `CPUVisible` segment. `D3D12_HEAP_TYPE_GPU_UPLOAD` (retail since Agility SDK 1.613.0, Mar 2024) is that memory in DX12: write-combined, "reads are inefficient", requires ReBAR on discrete cards. NVIDIA's post restricts it to buffers "the CPU never reads from" and reports one Watch Dogs: Legion vertex buffer going from 0.2 ms to under 0.01 ms of GPU time, ~0.9% of the frame; NVIDIA's ReBAR launch (Mar 2021) saw up to 12% in some titles and regressions in others, hence per-game profiles. Puget (Jul 2025): PCIe 4.0 x16 is 32 GB/s, 5.0 x16 is 64 GB/s; the RTX 5070 Ti is Gen 5 with 16 GB GDDR7, the RTX 3080 Gen 4.
*Bearing:* ReBAR is a latency and copy-count win worth single-digit percent; Forge uses it for constants, instance and indirect data and keeps bulk streaming on the transfer queue.

**NVIDIA. "Vulkan Do's and Don'ts"; "Advanced API Performance: Memory and Resources" and "Async Copy," 2021; Khronos. `VK_EXT_memory_budget`.** [docs] [still-current]
https://developer.nvidia.com/blog/vulkan-dos-donts/ — https://developer.nvidia.com/blog/advanced-api-performance-memory-and-resources/ — https://developer.nvidia.com/blog/advanced-api-performance-async-copy — https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html
"vkAllocateMemory() is an expensive operation on the CPU", so sub-allocate; query `VK_EXT_memory_budget` (extension 238; per-heap `heapBudget`/`heapUsage`) to stay ahead of OS demotion, and use `VK_EXT_pageable_device_local_memory` to mark critical resources high priority and vertex buffers low. Memory and Resources: reuse heaps with placed/reserved resources, keep compressible depth and large render targets apart from block-compressed textures when aliasing, move tile-mapping updates to the async copy queue at 2 MB granularity. Async Copy: the copy engine "is generally built to saturate PCIE bandwidth"; never put work there that is needed immediately, and local GPU-to-GPU copies do not belong on it.
*Bearing:* Forge polls `heapBudget` every frame, assigns memory priorities (attachments high, VT and cluster pools low) and schedules copy-engine work frames ahead.

**O'Donnell, Y. "FrameGraph: Extensible Rendering Architecture in Frostbite." GDC 2017.** [talk] [foundational]
https://www.gdcvault.com/play/1024612/FrameGraph-Extensible-Rendering-Architecture-in — slides: https://www.slideshare.net/DICEStudio/framegraph-extensible-rendering-architecture-in-frostbite
A graph of every pass and resource compiled each frame; transients ("alive for no longer than one frame") are acquired before first use and released after last use so passes alias physical memory: 720p PS4 fell from 147 MB to 77 MB and 4K DX12 PC from 1,042 MB to 472 MB.
*Bearing:* Forge's render graph carves transients from a per-frame linear VRAM heap using graph-derived lifetimes; modest on 16 GB, but it removes transient churn from the TLSF heap.

**Khronos. Vulkan specification, "Sparse Resources"; NVIDIA Developer Forums, "Sparse texture binding is painfully slow," 2023–2025; Sawicki, A. "Vulkan sparse binding – a quick overview," 2018.** [docs] [web] [still-current]
https://docs.vulkan.org/spec/latest/chapters/sparsemem.html — https://forums.developer.nvidia.com/t/sparse-texture-binding-is-painfully-slow/259105 — https://www.asawicki.info/news_1698_vulkan_sparse_binding_-_a_quick_overview
Standard sparse image blocks are 64 KB (128×128 texels at 32 bpp), bound in `vkQueueBindSparse` batches synchronized with semaphores. Sawicki (Dec 2018): sparse avoids fragmentation and recreation, but binding "is a queue operation" with "significant performance overhead". The NVIDIA thread (opened Jul 2023) reports ~250 µs per single page bind and tens of milliseconds for 1–10 K pages, with cost proportional to pages already bound across all sparse textures; NVIDIA acknowledged it, said a fix was "well under way" (Apr 2024), then "priorities shift" (Apr 2025), and a Linux regression between drivers 550 and 570 was reported in June 2025 with no fix confirmed.
*Bearing:* Sparse residency is not a runtime paging mechanism for Forge in 2026 on either vendor; virtual textures and cluster pages use software page tables over ordinary sub-allocated pools.

**Viau, G. "DX12 Memory Management in Snowdrop on PC." GDC 2024 (Massive Entertainment).** [talk] [recent]
https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Viau_Gauthier_DX12+Memory+Management.pdf
Snowdrop has no texture budget or quality setting: the streamer takes whatever the OS budget (`QueryVideoMemoryInfo`, "also available on Vulkan") leaves after ~4 GB of base VRAM at 1080p (~5.9 GB allocated on an 8 GB card, ~1.2 GB allocated-but-unused from fragmentation) and evicts mips below a safety margin. Over-commitment: VidMM suspends the GPU while demoting heaps over PCIe, then the GPU runs from system memory (a 16 GB/s bus at 54.7% read utilization, ~1.95 GB moved in one 223 ms frame, 5 fps for seconds; VidMM took 9 s to place one heap as 256 MB + 96 MB pieces). Fixes: Microsoft's residency library (works, but bindless resources must be enumerated and it can stall the CPU) and, better, tiled resources with 64 KB tiles so single mips can be evicted instead of whole 256 MB heaps.
*Bearing:* Take the budget from the OS, keep heaps small enough to place, evict at page granularity, make bindless residency explicit; the ~2 GB/s crawl is what over-commitment does to a 16 GB card.

## 3. Streaming from SSD: I/O, decompression, consoles

**Microsoft. DirectStorage for Windows 1.0–1.4. 2022–2026.** [docs] [code] [recent]
https://learn.microsoft.com/en-us/windows/win32/dstorage/dstorage-portal — https://github.com/microsoft/DirectStorage — https://github.com/microsoft/DirectStorage/blob/main/Docs/DeveloperGuidance.md — https://devblogs.microsoft.com/directx/directstorage-1-1-now-available/ — https://devblogs.microsoft.com/directx/directstorage-1-2-available-now/ — https://devblogs.microsoft.com/directx/directstorage-1-3-is-now-available/ — https://devblogs.microsoft.com/directx/directstorage-1-4-release-adds-support-for-zstandard/ — https://www.nuget.org/packages/Microsoft.Direct3D.DirectStorage
A queue API for NVMe drives that deliver "multiple gigabytes a second of small (for example, 64kb) data reads with minimal CPU overhead". 1.1 (Nov 2022) added GPU decompression with GDeflate on any DX12 Shader Model 6 GPU (64 KiB tiles, ~128 MiB staging to saturate I/O, CPU fallback); 1.2 (Apr 2023) buffered I/O for HDDs; 1.3 (Jun 2025) `EnqueueRequests` batches signalled by a D3D12 fence; 1.4 (public preview 11 Mar 2026) adds Zstandard on CPU and GPU with the GPU shader open-sourced (tuned for chunks ≤256 KB), the Game Asset Conditioning Library (BCn bit-stream shuffles and entropy reduction, "up to a 50% improvement in Zstd compression ratios", reversed at runtime for BC1/3/4/5) and D3D12 CreatorIDs, with vendor driver tuning promised for H2 2026. Guidance: ≥32 KiB per request, batch everything, queues at ~2× peak in-flight, no dependency chains. Destinations are D3D12 resources or CPU memory only.
*Bearing:* For a Vulkan engine DirectStorage is a reference design and parts bin (GDeflate and Zstd shaders, GACL transforms, request rules), not a runtime; Forge rebuilds the pipeline with unbuffered 64 KiB+ reads, GPU decompression in compute and fence-signalled batches.

**NVIDIA. "Accelerating Load Times for DirectX Games and Apps with GDeflate for DirectStorage," 2022; RTX IO; Khronos. `VK_NV_memory_decompression` → `VK_EXT_memory_decompression` and `VK_KHR_copy_memory_indirect`, 2025.** [web] [docs] [recent]
https://developer.nvidia.com/blog/accelerating-load-times-for-directx-games-and-apps-with-gdeflate-for-directstorage — https://developer.nvidia.com/rtx-io — https://www.khronos.org/news/permalink/nvidia-ships-vulkan-extensions-to-support-accelerated-rtx-io-on-windows-and-linux — https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_decompression.html — https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_copy_memory_indirect.html — sample: https://github.com/nvpro-samples/vk_memory_decompression — reference codec: https://github.com/microsoft/DirectStorage/tree/main/GDeflate
GDeflate (Nov 2022) is DEFLATE re-ordered so a 32-lane group decodes one 64 KB tile cooperatively; uncompressed streaming tops out near 3 GB/s on PCIe 3.0 and CPU DEFLATE becomes the bottleneck, whereas GPU decompression multiplies effective bandwidth by the ratio with "the CPU … fully available"; the reference codec is on GitHub under a permissive license. RTX IO's Vulkan path shipped Dec 2022 in Vulkan 1.3.233 as `VK_NV_memory_decompression` (428) and `VK_NV_copy_memory_indirect` (427), used by Portal: Prelude RTX (44% smaller install) and Ratchet & Clank: Rift Apart. Both were promoted: `VK_EXT_memory_decompression` (551, ratified 23 Jan 2025, `GDEFLATE_1_0`, `vkCmdDecompressMemoryEXT` plus an indirect-count variant) and `VK_KHR_copy_memory_indirect` (550, 25 Jan 2025, NVIDIA/AMD/Qualcomm/Valve/Collabora contributors).
*Bearing:* On both dev GPUs Forge decompresses GDeflate with one command; the EXT is the portable target, a compute decoder the fallback, and indirect copies let a GPU request list scatter pages without a CPU round trip.

**Ay, A. E. VolcanStorage. GitHub, 2025–2026; projectkml. `gdeflate` crate.** [code] [recent]
https://github.com/ahmetenesay/VolcanStorage — https://docs.rs/gdeflate/latest/gdeflate/
VolcanStorage v1.0 (MIT) is a DirectStorage-shaped runtime for Vulkan 1.1–1.4: a bundled GLSL compute GDeflate decoder, CPU fallback, timeline semaphores, IOCP on Windows and `pread` on Linux, automatic ReBAR/UMA detection to stream direct-I/O chunks into host-visible VRAM; no throughput numbers published. The `gdeflate` crate 0.4.1 binds the C reference, is "experimental", single-threaded and undocumented.
*Bearing:* Proof that a Vulkan-native DirectStorage is a few thousand lines; Forge writes its own in Rust and uses the crate only in the cooker.

**RAD Game Tools (Epic). Oodle Kraken, Mermaid, Selkie; Giesen, F. "Oodle, Kraken etc. misconceptions," 2024; Bloom, C. "How Oodle Kraken and Oodle Texture supercharge the IO system of the Sony PS5," 2020.** [web] [still-current]
https://www.radgametools.com/oodlekraken.htm — https://www.radgametools.com/oodlemermaidselkie.htm — https://fgiesen.wordpress.com/2024/08/08/oodle-kraken-etc-misconceptions/ — http://cbloomrants.blogspot.com/2020/09/how-oodle-kraken-and-oodle-texture.html
Kraken compresses like LZMA/Brotli-class codecs while decoding 3–5× faster than zlib; Mermaid is 7–12× faster than zlib; Selkie 1.5–2× faster than LZ4. Giesen (Aug 2024, Oodle co-author): Kraken's edge over older formats is "10-15% or so"; smaller PS5 packages come mainly from packaging tools removing the duplication PS4 needed for HDD seeks; Oodle Texture RDO makes BCn "more than 2x" more compressible without changing VRAM. Bloom (Sep 2020): PS5 reads 5.5 GB/s raw, 8–9 GB/s typical after the hardware Kraken decoder, ~22 GB/s peak; Kraken plus Oodle Texture reached 3.16:1 against 1.64:1 for zip. Licensing is commercial.
*Bearing:* Packaging without duplication beats the codec, and conditioning BCn before LZ is where the 2× lives, which Microsoft's GACL now offers free.

**Collet, Y. et al. Zstandard and LZ4; Kapoulkine, A. meshoptimizer vertex/index codecs.** [code] [still-current]
https://github.com/facebook/zstd — https://github.com/lz4/lz4 — https://github.com/zeux/meshoptimizer
The zstd README (Silesia, one core): zstd 1.5.7 `-1` ratio 2.896 at 1,550 MB/s decompression versus LZ4 1.10.0 at 2.101 and 3,850 MB/s; LZ4's table adds LZ4 HC `-9` at 2.721 and 4,900 MB/s decode; decompression speed is independent of level for both. meshoptimizer's vertex codec gets 2–4× on quantized data, its index codec ~1–1.2 bytes per triangle, both decoding at 3–6 GB/s per core ahead of LZ4, zstd or Oodle.
*Bearing:* One core decodes ~1.5 GB/s of zstd or ~4 GB/s of LZ4; a 16-core dev PC can out-decode a 7 GB/s NVMe on the CPU, so GPU decompression here is a CPU-headroom choice, not a necessity.

**Karis, B., Stubbe, R., Wihlidal, G. "A Deep Dive into Nanite Virtualized Geometry," streaming section. SIGGRAPH 2021.** [talk] [foundational]

The streaming unit is the cluster group, packed into fixed 128 KB pages by spatial locality and DAG level and split at cluster granularity (~2 KB clusters, ~1% slack); the root page is always resident, and the whole culling hierarchy stays resident so traversal can request every level beyond the streaming cut at once. ## 5. Asset formats and packaging

**Epic Games. "Zen Loader in Unreal Engine" (IoStore). Unreal Engine documentation, 2022–2026.** [docs] [still-current]

## Recommendation for Forge

**CPU memory.** Three tiers, all instrumented through Tracy's `ProfiledAllocator`. (1) A tagged block heap in Gyrling's shape: 2 MiB blocks carved from one reserved 64 GB virtual range (Fleury), committed on demand, one current block per worker thread, tags of `(frame_index, stage)` for per-frame data and `(cell_id)` for streamed world cells (Fredriksson's scope semantics, `Drop` in reverse), freed in bulk. (2) Pools with `slotmap` handles for fixed-size long-lived objects (entities, cluster pages, VT pages, I/O requests). (3) `mimalloc` as `GlobalAlloc` for the long tail and third-party crates, with a Tracy pool per crate so the pie chart always adds up. Budgets are declared per system and reported every frame; anything over 5% of RAM without a budget is a bug. When Rust 1.100 lands, frame containers become `Vec<T, &FrameArena>`; until then `bumpalo`.

**GPU memory.** Heaps are classified at startup as UMA, discrete, or discrete-with-ReBAR (the dev PC). VRAM is sub-allocated from 256 MiB blocks by a TLSF allocator with size-classed pools (small buffers, large buffers, images, attachments), dedicated allocations only for attachments and anything over 64 MiB; `gpu-allocator` stays until the TLSF layer exists. Budget = `heapBudget` minus a 10% reserve, re-read every frame; memory priorities mark attachments and root cluster pages high, the VT and cluster pools low. Aliasing is the render graph's job: transients come from a per-frame linear heap laid out from graph lifetimes. Defragmentation runs on the transfer queue at a fixed budget (start at Guerrilla's 16 MiB per frame), moved blocks linger one frame, descriptors are patched the next. What lives in ReBAR memory: only the per-frame ring, a few MiB of constants, instance transforms, indirect arguments and GPU request buffers, written once sequentially with 64-byte alignment from a CPU shadow and never read back; readback goes to `HOST_CACHED` memory. Everything bulk (cluster pages, VT pages, meshes, textures) is staged and copied by the transfer queue at least two frames before use, or written by GPU decompression straight into its pool. Without ReBAR the ring falls back to staging; on UMA it maps directly. Sparse binding is not used at runtime.

**Streaming architecture.** One I/O thread per NVMe drive runs an IOCP/IoRing loop (io_uring on Linux) issuing unbuffered, sector-aligned reads of whole pages (128 KB cluster pages, 64–256 KB VT tiles, 256 KiB archive blocks), 32–64 in flight, from archives kept open with an in-memory table of contents. A request scheduler merges three sources: GPU cluster-page requests (Nanite's persistent-shader output with LOD-error priority, read back asynchronously), VT feedback (a depth-tested pass at a tenth of the resolution) and CPU prefetch (cells along the velocity vector, cutscene cameras, teleports). Priority is need (screen error, distance-scaled as in Widmark), resident pages re-score every frame, and eviction takes the lowest-need page, never the least recently used one: this is the specific fix for the old 3,072-slot pool. Decompression: GDeflate through `VK_EXT_memory_decompression` on both dev GPUs (compute decoder fallback) under a per-frame decompression budget; a CPU zstd/LZ4 path serves tools and the UMA case and, at ~1.5 GB/s per core, could sustain the drive on 16 cores by itself, so the GPU path is chosen to keep cores free rather than to reach bandwidth. Zstandard replaces GDeflate once Microsoft's open Zstd shader and vendor drivers settle (H2 2026). Per-frame upload budget: 64 MB at 60 Hz on the transfer queue, 3.8 GB/s, below both PCIe 4.0 (32 GB/s) and the drive; hitches are prevented by never waiting on I/O inside the frame and by the always-resident root pages and coarsest VT mips.

**Asset container.** A cooked world is a set of archives: a `.toc` (chunk id → offset, compressed and uncompressed size, codec, BLAKE3 hash, dependency edges computed at cook time) and `.cas` blobs of 256 KiB compressed blocks ordered depth-first by dependency graph (Guerrilla) so a cell is one contiguous read. Chunks are content-addressed by BLAKE3 with XXH3-64 runtime keys, so identical clusters and tiles are stored once. Textures are KTX2 with per-level supercompression (BC7/BC5/BC6H, GACL-style channel shuffles before zstd where they help); meshes are meshoptimizer-encoded quantized clusters followed by GDeflate/zstd; everything is 4 KiB-aligned so a page lands in its final buffer without a shuffle.

**The demo that proves it.** A 64 km² procedural world with unique virtual-textured terrain, a million cluster-DAG instances and a GPU-placed forest, flown at 300 m/s at 1440p on the RTX 5070 Ti and the RTX 3080, with an on-screen dashboard of resident cluster pages, VT pages, VRAM by pool against `heapBudget`, drive throughput, decompression throughput, request queue depth and the 99th-percentile frame time. Pass criteria: zero frames over 20 ms across a 10-minute flight; no visible LOD or texture pop at 300 m/s (screen error below one pixel for everything resident); resident memory flat within 5% of budget; the same flight replayed with the drive throttled to 1 GB/s degrades to blur, never to hitches. If it passes, the streaming layer is done and the world can grow.

- **The budget query is not free.** `vkGetPhysicalDeviceMemoryProperties2` with the
  budget structure costs 8–10 µs on this machine (the driver asks the OS). That is 3 % of
  a 0.2 ms CPU frame if it ran every frame, so the overlay reads it four times per second
  and on captured frames. "Polls `heapBudget` every frame" above becomes "every few
  frames" until a streaming scheduler needs it more often.
- **Block size dominates small scenes.** `gpu-allocator`'s default 256 MiB device and
  64 MiB host blocks put both demos at 357 MiB of VRAM for 43 and 108 MiB of data (14 %
  and 28 % of the blocks used). The TLSF layer with size-classed pools is where that
  changes; until then, the process's usage says more about the allocator than the scene.
- **Per-frame data is in VRAM.** On this Resizable BAR system every `CpuToGpu` allocation
  lands in the device-local heap. The first host-visible block is therefore 64 MiB of VRAM
  for 0.5 MiB of per-frame data.
- **What the process holds outside the allocator can dwarf what it allocates.** 50 MiB
  of driver memory and swapchain images, 111 MiB more once Streamline is loaded (even with
  DLSS unused), and 155–203 MiB more with the DLSS feature running at a 1600×900 output.
  Only `heapUsage` sees any of it, which is why the budget has to come from the OS, not
  from the engine's own tally.
- **The upload counter measures the host side only.** It counts bytes the CPU writes
  through mapped pointers. Staging copies on the GPU are not counted twice: the ballad
  writes 1.1 KiB per frame, and the overlay's cell grid adds 31 KiB.
